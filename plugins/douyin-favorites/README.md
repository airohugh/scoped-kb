# 思路：把抖音收藏接进来（仅说明，无可运行代码）

这里只写方法和输入格式，不给出采集脚本、不写签名参数、不写接口路径、不写 cookie 名。原因见下面"平台条款"一节。

## 方法

思路是让**已登录的浏览器自己完成签名**，脚本只做两件事：驱动浏览器翻收藏列表，和拦截浏览器发出的网络响应——不自己拼接请求、不自己计算任何签名参数。具体来说：

1. 用一个已经登录你自己账号的浏览器会话（不是无头、不伪造 UA，就是你平时用的那个登录态）；
2. 在浏览器侧翻动"收藏"页面，触发它自己去加载列表数据；
3. 脚本只拦截浏览器发出请求后收到的响应内容，解析出你关心的字段（标题、作者、原始链接、文本描述、发布时间等），不去反推接口怎么构造、不去模拟签名算法；
4. 对每条收藏，脚本自己写一个 `.md` 文件，落进一个专门的 collection（建议 `kind_default: raw`，因为这是外部采集的内容，不是你自己的产出）。

## 输出格式建议

```markdown
---
trust_tier: T3
source_url: <原始视频/图文链接>
captured_at: <采集日期>
---

## <标题或前 N 个字的摘要>

<文本描述、转写或你自己摘录的要点>
```

视频本身不进 `.md` 文件（这是文本知识库，不存媒体）。如果你额外跑了语音转写，完整逐字稿建议按 `plugins/README.md` 第 4 条用 `<!-- no-index -->` 包起来，只把你自己提炼的要点放进会被索引的小节。

`trust_tier` 默认建议标 T3（社区/二手，未经核实）——收藏本身只是"你觉得这条有意思"，不代表内容已经核实过。

## 平台条款——使用前自己确认

抖音的用户协议里有条款限制对其内容和接口的自动化采集（以你使用时的当前版本协议原文为准，条款编号和具体措辞会随协议更新变化，不要依赖这份文档里的任何版本号）。这个方向的自动化是否合规、风险多大，需要你自己读一遍当前生效的协议原文再决定要不要做，并自行承担后续责任——这不是本仓能替你判断的事。本仓不提供、也不会提供可直接运行的采集代码，就是为了避免把"提供自动化采集工具"这件事变成本项目的默认立场。
