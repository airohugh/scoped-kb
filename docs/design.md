# 设计说明：为什么这样做

这份文档回答"为什么"，不是"怎么用"（用法在 README）。四个问题：为什么只做纯向量检索、为什么要有世代门、出处信息为什么只在呈现层、为什么要分两层 scope。

## 为什么只做纯向量检索，不做关键词混合

直觉上关键词检索（BM25 之类）该能补上向量检索在短查询、专有名词、型号这类"精确匹配比语义相似更重要"的场景里的弱点。但混合检索要多付三样代价，而且都不是一次性成本：

1. **排序融合参数**要调——向量分数和关键词分数的量纲不一样，简单加权几乎总是偏向其中一边，调好了也会随语料分布漂移；
2. **索引**要双写——倒排索引和向量索引各自维护，分块策略变了（比如改切块大小）两边都要重建，增量索引的复杂度直接翻倍；
3. **中文分词**是额外的坑——关键词检索依赖分词边界，中文没有空格天然分隔，分词器选型本身又是一个要维护的依赖。

本仓的定位是"单人或小团队用的本地知识库核心"，不是搜索引擎。纯向量把这三样代价都省掉了，换来的代价写在已知限制里：短术语、型号这类查询确实弱于关键词检索。如果你的笔记里有大量型号、代号这类需要精确命中的内容，这是需要你自己评估的取舍，不是这个项目要去解决的通用问题。

## 为什么要有世代门（generation gate）

`knowledge_index_meta` 只存一行：当前索引是用哪一份配置（`registry_hash`）构建出来的。检索前必须核对这个 hash 与"本次调用现算出来的配置"一致，不一致就拒绝返回结果，而不是"先返回能查到的，提示一下可能不准"。

理由是分域的前提是"索引里每一行的 `collection_id` 都准确反映当前配置下它该归属哪个域"。配置变了（比如把一个 collection 从 `active` 改成 `quarantine`，或者调整了某个 profile 的 allowlist）但索引还没跟着重建，这时候索引里的归属信息就是过期的——继续用旧索引服务新配置下的查询，后果是两个方向都危险：

- 该被隔离的内容可能还挂着旧的 `active` collection_id，被新配置下本不该读到它的 profile 查到；
- 新配置收紧了某个 profile 的权限，但旧索引里的行还按旧的宽松归属存在，查询方看到的权限边界和配置文件里写的不一致。

两者都不是"结果不够新"这种可以容忍的降级，是"访问控制的边界本身失效了"。所以世代不一致时统一拒绝（`ScopeError`，退出码与"无命中"的 0 区分开），提示运行 `scoped-kb index`——它检测到配置变化会自动全量重建，所以这不是一个需要用户额外记住的步骤，只是一个明确的报错优于沉默服务错误结果。

## 为什么出处信息只在呈现层渲染，不进 embedding

一条笔记的可信度标签（`trust_tier`、`source_url`、`captured_at`）如果写进 `content` 列参与 embedding，会带来两个问题：

1. **污染排序**——"这条内容来自哪里"和"这条内容说了什么"是两个独立的维度，混进同一个向量会让检索排序受到元信息的影响，而这个影响没有办法单独调节或关掉；
2. **耦合索引生命周期**——出处信息一旦进了 embedding，要修正一条笔记的 `trust_tier`（比如后来确认了某个 T3 来源其实是官方一手资料）就意味着要重新向量化这条内容，即使正文一个字都没变。

真正的痛点——"检索结果里分不清哪些是自己验证过的判断、哪些是外部抓来的转述"——完全发生在"这段文本最终呈现给谁看"那一步，不发生在"这段文本和查询语义有多像"那一步。所以做法是：`content` 列只存裸正文参与排序；出处字段留在源文件的 YAML frontmatter 里，`search` 命令在渲染结果时才回读文件、按配置里 `provenance_fields` 声明的字段白名单取值、拼成一行"出处：…"附在每条结果后面。这也是为什么换一次 `trust_tier` 标注不需要重新索引——它从来没进过向量。

代价是每次 `search` 多一次文件读取（忽略不计的开销），好处是出处渲染规则可以独立于索引生命周期随时调整，而且天然不会因为"出处写错了"污染排序结果。

## 为什么 `pack` 的凭据守卫只报不改

`pack` 产出的那一包是要粘给外部 agent 的，粘出去就收不回来。守卫检出疑似凭据时直接中止，不替你打码。原因有两条：

1. **静默脱敏会制造虚假安心**。被改过的包和没改过的长得一样，人会以为安全了，实际只是没看见。中止会逼人回源文件看一眼：是真凭据就该从笔记里删掉或换掉（笔记里放着凭据，问题不只在这一包）；是误报再用 `--force` 放行。
2. **正则覆盖不全**。没有字段名提示的裸密码这类东西，任何基于形态的扫描都会漏。要是自动脱敏，用户会默认「包里有的都处理过了」；只报不改，用户就知道它只是一道网。

守卫的报告也不回显命中的原文，只给行号、所在片段、规则类别和前几位掩码。字段名同样不回显，它也来自被扫的文本，里面可能就夹着密钥。报告会进终端、CI 日志和聊天记录，把原文打出来就等于守卫自己泄露了它要拦的东西。命中行属于哪个片段，按渲染时记下的行区间查，不回头解析包里的「### 来源」标题，因为正文里同样能写出这样一行。报告也不打文件路径，只给片段序号：文件名里同样可能写着密钥，而「一个路径像不像凭据」没有可靠的判法。

排除项（占位符、代码引用、普通词等）一律按完整形态匹配整个值。只看首字符会放过 `password=$<随机串>` 这类明确的赋值。一条匹配被排除项放过时，守卫从它的值的起点接着扫，不把整段跳过：`token_url: https://…#access_token=<随机串>` 外层因字段名被放过，里面的 `access_token=` 照样会被检出。

规则怎么改：每条规则、每个前缀分支、每个关键词、每个排除项在 `tests/secret_samples.py` 里都有正例或负例守着。删掉任何一条，或把排除项放宽，对应的用例会变红。加规则时同时加样本，样本按「要抓什么、不该抓什么」写，不要对着正则造。

## 为什么要分两层 scope：仓库声明 + 中央策略

单人单仓库场景不需要分域，`scoped-kb init` 把这一层机制隐藏掉了——本质上是生成了一个"一个 collection、一个 profile、谁都能读"的最简配置。但这套机制存在的原因，是给"同一台机器上同时服务多个互不信任边界"的场景：比如你同时在用两家不同的 AI agent，一个专门处理工作笔记，另一个专门处理个人阅读笔记，你不想工作笔记的内容被阅读笔记那边的 agent 检索到，反过来也一样。

核心设计约束是**放置位置不授予权限**：一份"仓库声明"（`collections.json` 或 `machine-sources.json`）只能回答"这个目录里有什么、它们的默认性质是什么"，不能回答"谁被允许读它"。能决定"谁被允许读它"的字段（`scope`、`authority`、`index_policy`、`profiles`、`cross_allowlist`、`fingerprint`……）只能出现在"中央策略"（`scope-policy.json`）里；仓库声明里一旦出现这些字段，编译直接报错，不存在"本地声明覆盖中央策略"这种口子。

这个约束要解决的具体问题是：如果权限字段也能写在仓库声明里，那么一个仓库只要在自己的 `collections.json` 里新增一行、把自己的某个目录标成别的 profile 能读，就等于自己给自己扩大了访问范围——这完全绕开了"谁能读什么"本该由谁拍板的问题。两层拆开之后，仓库声明的变更（比如新增一个目录）必须经过中央策略显式确认（指纹核对不过编译直接失败），不存在"改了声明立刻生效"的隐式扩权路径。

### 指纹（fingerprint）防什么

中央策略对每个 collection 钉住一份"声明指纹"——对规范化后的实际 roots（`realpath` 之后的绝对路径）和 excludes 算哈希，不是对配置文件里的原始字符串算哈希。原因是三种改动都不改那行配置文本、却能换掉它实际指向的目录：改上层目录变量、把某个目录换成指向别处的符号链接、路径里混入 `..` 或大小写差异。如果指纹钉的是原始字符串，这三种改动都能在"声明文本没变"的伪装下悄悄扩大实际被索引、被授权的范围。

### 跨域（cross）为什么比同域多三道手续

同域查询（cwd 落在某个已注册的仓库根下）不需要任何额外参数，查询范围由该域的 profile 决定。跨域（`--profile cross --include <域> --why "原因"`）是显式扩大读取范围的动作，要求：

1. **目标组合必须在中央 `cross_allowlist` 里**——不存在"只要双方都同意就能跨"的隐式路径，组合必须被中央策略显式登记；
2. **`--why` 必须非空**——跨域发生的理由要留痕，否则事后没法判断这次扩权合不合理；
3. **可追溯 ID（任务 ID / 会话 ID）必须存在**——通过环境变量提供，缺失就拒绝执行而不是留空占位。留占位的后果比不记录更糟：它会让"这次跨域发生过"这个事实看起来已经被记录了，但实际上断了链，追责和复盘都无从下手。

每一次**合法的**跨域尝试，不论最后有没有查到结果、有没有被别的检查挡住，都会在状态目录的 `cross-domain.jsonl` 里追加一行留痕（只记查询字符数，不记查询内容本身）。例外：已经写下 ok 行、但往终端或文件交付结果时失败，会再补一行 failed（交付成功之后的提示信息写失败不算），所以一次尝试最多两行。只在成功交付结果时才记录的话，会让"范围已经被扩开过"这件事在失败路径上变得不可见——而失败路径（比如被世代门拦住）同样是一次真实发生过的扩权尝试，必须留痕。

### 威胁模型边界

分域隔离防的是**配置与归属错误**：拼错路径、把目录挂到错误的域、符号链接把别处的内容带进本域、改了配置却没重新索引。它不防**对笔记目录有写权限的本地对手**——能写笔记目录的人本来就能把任何内容直接写进任何 collection。具体例子：扫描做完边界检查、到真正读取文件之间有一个窗口，若有人在此期间把文件换成指向域外的链接，域外正文会被索引进来；本项目不为此做基于目录描述符的安全打开，因为堵住这个窗口得不到额外的隔离。同理，本机与数据库本身也被当作可信的：能直接连库的人可以绕过所有分域检查。
